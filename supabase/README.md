# Supabase DB 스크립트

이 폴더에는 이 도구의 저장 데이터를 PostgreSQL(Supabase)로 옮길 때 쓰는 스키마가 들어 있습니다.
지금 도구는 아직 브라우저 저장소(localStorage)만 씁니다.
DB 에 연결하는 코드는 다음 단계에서 붙입니다.

## 왜 DB 가 필요한가

지금은 모든 저장값이 브라우저 localStorage 의 `data09-11.db` 한 칸에 들어 있습니다.
그래서 다음과 같은 한계가 있습니다.

- **일정표를 한 사람만 갱신합니다.** 기획서의 현안이 바로 「개발 기종 일정표를 한 명이 갱신하는 방식」입니다. 브라우저 저장소에 두면 이 구조가 그대로 남습니다. DB 에 두어야 다음 단계에서 여러 담당자가 같은 현황표를 보고 고칠 수 있습니다.
- **이슈 이력이 사라질 수 있습니다.** 이슈 번호(ISS-0001 …), 조치 내용, 종결일, 근거 메일(MSG) 링크는 나중에 다시 찾아볼 기록입니다. 브라우저 데이터를 지우거나 PC 를 바꾸면 함께 사라집니다.
- **기종·단계·일정·이슈·자료가 서로 얽혀 있습니다.** 기종을 지우면 그 일정·이슈·자료도 지워야 하고, 쓰는 중인 단계는 지우면 안 됩니다. 지금은 화면 코드가 이것을 지키지만, DB 에서는 외래키가 같은 규칙을 한 번 더 지켜 줍니다.
- **기종이 늘면 저장이 실패합니다.** localStorage 는 보통 5MB 안팎입니다.

사내 자료는 외부 AI 에 보내지 않는다는 원칙(기획서 3장)은 DB 로 옮겨도 그대로입니다.
이 스키마는 본인 Supabase 프로젝트에만 저장하며 외부 AI 로 보내는 부분이 없습니다.

## 테이블

| 테이블 | 용도 | localStorage 대응 |
|---|---|---|
| `workspace` | 임박 기준 일수, 일정 Excel 열 이름 매핑, 예시 여부 (1인 1행) | `data09-11.db` 의 `settings` · `_sample` |
| `model` | 개발 기종 | `data09-11.db` 의 `models[]` |
| `stage` | 공통 개발 단계 (순서 있음) | `data09-11.db` 의 `stages[]` |
| `schedule` | 기종 × 단계 일정 (한 칸에 하나) | `data09-11.db` 의 `schedules[]` |
| `issue` | 이슈와 근거 첨부 | `data09-11.db` 의 `issues[]` |
| `doc` | 기종·단계별 자료 목록 (파일은 링크로만) | `data09-11.db` 의 `docs[]` |
| `bm` | 과제 A Bench Marking 조사 묶음 (브랜드·스펙 항목·공개 자료·요약 답변) | `data09-11.db` 의 `bm[]` |

필드 이름은 도구의 이름을 snake_case 로 그대로 옮겼습니다.
SQL 예약어와 겹치는 것만 바꿨습니다.

| 도구 | DB |
|---|---|
| `order` | `sort_order` |
| `start` · `end` | `start_date` · `end_date` |
| 각 레코드의 `id` | `model_id` · `stage_id` · `schedule_id` · `issue_id` · `doc_id` · `bm_id` |
| `modelId` · `stageId` · `repoLink` · `soonDays` | `model_id` · `stage_id` · `repo_link` · `soon_days` |

이 도구에는 변경 이력이나 로그 같은 기록성 데이터가 없습니다.

### 권한

- 모든 표에 RLS(행 수준 보안)를 켰습니다.
- 모든 행은 만든 사람만 보고 고칠 수 있습니다(`owner_id = auth.uid()`). `owner_id` 는 로그인한 사용자로 자동으로 채워집니다.
- 일정·이슈·자료는 `(owner_id, model_id)` 로 기종을 가리킵니다. 그래서 남의 기종 번호를 알아내도 거기에 일정이나 이슈를 붙일 수 없습니다.
- 로그인하지 않은 사용자(anon)는 어떤 표도 읽거나 쓸 수 없습니다.
- 도구의 규칙을 DB 제약으로도 막습니다.
  - 같은 이름(공백·대소문자 무시)의 기종·단계는 하나만 둡니다.
  - 한 기종·단계 칸에 일정은 하나뿐이고, 종료일이 시작일보다 빠를 수 없습니다.
  - 이슈 상태는 열림·조치중·종결 세 가지이며, 종결이면 종결일이 있고 아니면 없습니다.
  - 기종을 지우면 그 일정·이슈·자료도 지워지고, 쓰는 중인 단계는 지울 수 없습니다.
- 앱에서 upsert 할 때는 `onConflict` 를 표의 UNIQUE 조합으로 지정해야 합니다. 예를 들어 일정은 `owner_id,model_id,stage_id` 입니다.

지금은 한 사람의 자료만 다룹니다. 여러 담당자가 같은 일정표를 함께 쓰려면 팀 단위 권한을 더해야 합니다. 이것은 앱 연결 뒤에 정합니다.

## 적용 방법

1. <https://supabase.com> 에 가입합니다.
2. 새 프로젝트를 만듭니다. 이 도구 전용으로 본인 프로젝트를 쓰는 것을 전제로 하므로 테이블 이름에 접두사를 붙이지 않았습니다.
3. 왼쪽 메뉴에서 **SQL Editor** 를 엽니다.
4. `supabase/schema.sql` 의 내용을 전부 붙여넣습니다.
5. **Run** 을 누릅니다.

여러 번 실행해도 안전합니다. 이미 있는 표는 건너뛰고 정책·트리거는 지우고 다시 만듭니다.

## 확인 방법

1. 왼쪽 메뉴 **Table Editor** 에 위 7개 표가 보이는지 확인합니다.
2. 각 표 이름 옆에 RLS 가 켜져 있는지(「RLS disabled」 경고가 없는지) 확인합니다.
3. **Authentication → Policies** 에서 표마다 SELECT·INSERT·UPDATE·DELETE 정책 4개가 붙어 있는지 봅니다.
4. SQL Editor 에서 아래를 실행해 함수 권한에 `anon` 이 없는지 봅니다.

```sql
select proname, proacl from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public';
```

## 앱 연결은 다음 단계입니다

이 스크립트는 표와 권한만 만듭니다. 도구의 `js/store.js` 는 아직 localStorage 를 씁니다.
Supabase 에 저장하려면 다음 단계에서 로그인과 저장·불러오기 코드를 붙여야 합니다.

## 로컬 검증 방법

운영에서 처음 실행하지 않도록, 임시 로컬 PostgreSQL 에 실제로 적용해 검사하는 도구를 함께 두었습니다.

```sh
./scripts/sqltest/run.sh
```

PostgreSQL 16 이상이 필요합니다(macOS: `brew install postgresql@17`).
임시 DB 를 만들어 쓰고 끝나면 지우므로 기존 설치에는 영향이 없습니다.

검사 내용은 다음과 같습니다.

- 스키마를 두 번 적용해도 오류가 없는가
- 사용자 A 의 행이 사용자 B 에게 보이지 않고, 고치거나 지울 수도 없는가
- 남의 기종에 일정·이슈를 붙일 수 없는가
- 로그인하지 않은 사용자는 아무것도 읽거나 쓸 수 없는가
- CHECK·UNIQUE·외래키가 잘못된 값과 중복을 막는가
- 함수 실행 권한에 PUBLIC·anon 이 남지 않았는가

검사용 SQL(`scripts/sqltest/*.local.sql`)은 로컬 전용입니다.
Supabase 운영 DB 에서 실행하면 스스로 멈추도록 가드가 들어 있습니다.
